## Purpose

Surface a single app from the Shomri Hub App Store with rich details and an install flow, then expose app-level settings that respect device policy and user role.

- Present detailed information for a selected app and hand off installation to the Apple App Store.
- Expose app-related configuration for a device, with different behaviors for mentee/child versus self-managed devices.

<Callout kind="info">

The App Details page opens when the user taps an app card on the App Store page. The same underlying configuration API powers App Settings for both mentee/child and self-managed devices; the difference is how users change settings.

</Callout>

## App Details page layout

The App Details page mirrors an app store product page with a Shomri header and install controls.

### Entry point and navigation

- The user starts on the Shomri Hub **App Store** page (`/home-page`), which lists available apps.
- When they tap an app tile, open the **App Details** page for that app.
- Keep global navigation (sidebar/top bar) consistent so users can navigate back to the App Store.

### Key UI elements

Design the top of the App Details page around the app identity and a primary action.

- **Icon** — Large app icon, matching the App Store asset.
- **Name** — Human-readable app name (from metadata).
- **Publisher** — Developer or seller name under the title.
- **Category** — Primary category label (for example, Education, Utilities).
- **Rating** — Average rating score and count when available.
- **Primary action button** — Contextual label and state:
  - `Install` (app not installed)
  - `Installing` (installation in progress)
  - `Open` (installed on the current device)

Below the header and button, show:

- **Description** — Full app description, with optional "Show more" expand behavior.
- **Highlights** — Key capabilities as a short bullet list, when available.
- **Screenshots** — Horizontal scroll gallery, preserving App Store aspect ratio.
- **Policy/app settings entry** — Optional link or section leading to the App Settings view for this app on the current device.

### Install button states and flow

Use a clear, linear flow that matches the Shomri App install experience.

<Steps>

<Step title="Install" icon="download">

- Show an **Install** button when the app is not yet installed on the current device.
- When the user taps **Install**, trigger your `devices.apps.install` flow and, if needed, open the overlay that will deep-link to the Apple App Store.
- Immediately transition the button label and state to **Installing** to acknowledge the action.

</Step>

<Step title="Installing" icon="play-circle">

- While the install job runs, keep the button disabled and labeled **Installing`.
- Optionally show a lightweight progress indicator or spinner inside the button.
- Poll installation status with `apps.list.allOnDeviceWithStatus` or subscribe to your install tracking so you can move to **Open** when complete.

</Step>

<Step title="Open" icon="check-circle">

- After the install completes on the target device, update the button to **Open**.
- Tapping **Open** should:
  - On the managed device: open the installed app (for example, via a deeplink from the device agent).
  - On a management-only device: show instructions or confirmation, not the native app itself.
- If the app is later uninstalled, fall back to the **Install** state again.

</Step>

</Steps>

<Callout kind="tip">

Keep the primary button stable in layout; only change its label and state. This avoids layout shifts while the app moves between Install, Installing, and Open states.

</Callout>

## App Details data: Apple Lookup API

The App Details page uses metadata from Apple to stay in sync with the public App Store listing while letting Shomri control install behavior.

### Data source: Apple Lookup API

Use the Apple Lookup API to fetch app metadata based on the App Store `trackId`. Combine this with your own catalog fields (for example, Shomri-specific tags or policy defaults) when you build the page model.

#### Inputs

<ParamField query="trackId" param-type="number" required="true">

The Apple App Store identifier for the app. Persist this on the app record in your catalog and pass it to the lookup call.

</ParamField>

#### Outputs (metadata shape)

Treat the Apple Lookup API response as `metadata` for the UI. The exact Apple payload is large; pull out the fields you need for the App Details layout.

<ParamField body="metadata" param-type="object" required="true">

Container for the app metadata returned by the Apple Lookup API.

</ParamField>

<ParamField body="metadata.name" param-type="string">

Human-readable app name used for the header.

</ParamField>

<ParamField body="metadata.bundleId" param-type="string">

Bundle identifier for the app, used to correlate with device configuration and install status.

</ParamField>

<ParamField body="metadata.developerName" param-type="string">

Publisher or developer name displayed under the app name.

</ParamField>

<ParamField body="metadata.description" param-type="string">

Full description text displayed in the details section.

</ParamField>

<ParamField body="metadata.screenshots" param-type="string[]">

List of screenshot image URLs displayed in the gallery.

</ParamField>

<ParamField body="metadata.category" param-type="string">

Primary category label for the app.

</ParamField>

<ParamField body="metadata.rating" param-type="number">

Average rating score if available.

</ParamField>

<ParamField body="metadata.storeUrl" param-type="string">

Deep link URL to the app in the Apple App Store, used in the download overlay.

</ParamField>

#### Example: Apple lookup call

<CodeGroup tabs="Request,Response" show-lines={true}>

```bash
# Request: lookup app metadata by trackId
curl "https://itunes.apple.com/lookup?id=871761612"
```

```json
{
  "resultCount": 1,
  "results": [
    {
      "trackId": 871761612,
      "trackName": "Shomri Companion",
      "bundleId": "com.shomri.companion",
      "sellerName": "Shomri Labs Ltd",
      "description": "Shomri Companion helps families manage device usage and app access.",
      "primaryGenreName": "Utilities",
      "averageUserRating": 4.6,
      "screenshotUrls": [
        "https://is5-ssl.mzstatic.com/image/thumb/Screen1.png",
        "https://is5-ssl.mzstatic.com/image/thumb/Screen2.png"
      ],
      "trackViewUrl": "https://apps.apple.com/app/id871761612"
    }
  ]
}
```

</CodeGroup>

Map this response into the `metadata` shape your UI expects. For example, map `trackName` to `metadata.name`, `sellerName` to `metadata.developerName`, `primaryGenreName` to `metadata.category`, `averageUserRating` to `metadata.rating`, `screenshotUrls` to `metadata.screenshots`, and `trackViewUrl` to `metadata.storeUrl`.

When the user taps **Install** or **Open in App Store**, show an overlay that deep-links to `metadata.storeUrl` in the Apple App Store.

## App Settings view — Mentee/Child

The mentee/child App Settings view shows the current configuration for this app on a device and lets the user request, but not apply, changes.

<Callout kind="info">

Mentees cannot change policy directly. When they tap a setting they do not have, open a modal to submit a change request. The request then flows through your approval process.

</Callout>

### View configuration

Use `api.devices.apps.getConfig` to populate the App Settings view for a specific device. Link into this view from the App Details page when the user wants to understand why an app is blocked or request access.

#### Inputs

<ParamField body="deviceId" param-type="string" required="true">

Identifier of the device whose app configuration you are viewing.

</ParamField>

#### Outputs

<ParamField body="appMode" param-type="string" required="true">

Current mode for the device, such as focus or leisure. Use this to drive high-level messaging and which controls are enabled.

</ParamField>

<ParamField body="appFilter" param-type="string" required="true">

Active filter policy for apps, such as category-based or whitelist-only.

</ParamField>

<ParamField body="allowedApps" param-type="string[]" required="true">

List of app bundle identifiers that are explicitly allowed on the device.

</ParamField>

<ParamField body="blockedApps" param-type="string[]" required="true">

List of app bundle identifiers that are explicitly blocked on the device.

</ParamField>

#### Example: config fetch

<CodeGroup tabs="Request,Response" show-lines={true}>

```json
{
  "method": "api.devices.apps.getConfig",
  "args": {
    "deviceId": "dev_9f32b47c2a8f4f8a"
  }
}
```

```json
{
  "appMode": "guided",
  "appFilter": "categories",
  "allowedApps": [
    "com.shomri.companion",
    "com.duolingo.DuolingoMobile"
  ],
  "blockedApps": [
    "com.supercell.clashofclans"
  ]
}
```

</CodeGroup>

Render sections for AppMode, Categories, Whitelist, Blacklist, and Network Rules. For mentees, keep these sections mostly read-only, with entry points into the request flow when they tap something they want to change.

### Request app or policy change

When a mentee interacts with a configuration they do not have (for example, tapping a blocked app they want to allow from the App Details page or App Settings view), trigger a modal.

#### Modal behavior

- Show the current value and the requested new value.
- Let the mentee specify a reason (optional).
- On submit, call `request.create.appRequest`.

<Callout kind="tip">

Define additional request types for specific changes, such as network rules updates or mode changes. Keep the modal flexible to support multiple `type` and `target` values.

</Callout>

#### Inputs

<ParamField body="deviceId" param-type="string" required="true">

Device the request applies to.

</ParamField>

<ParamField body="type" param-type="string" required="true">

Kind of change requested, such as `allowApp`, `blockApp`, or `changeMode`.

</ParamField>

<ParamField body="target" param-type="string" required="true">

Identifier for what is changing. For app changes, use the app bundle identifier; for mode changes, use the target mode name.

</ParamField>

<ParamField body="reason" param-type="string" required="false">

Free-text explanation from the mentee about why they are requesting the change.

</ParamField>

#### Outputs

<ParamField body="requestId" param-type="string" required="true">

Unique identifier for the created request, used to track approval status.

</ParamField>

<ParamField body="status" param-type="string" required="true">

Initial status of the request, such as `pending`.

</ParamField>

#### Example: change request

<CodeGroup tabs="Request,Response" show-lines={true}>

```json
{
  "method": "request.create.appRequest",
  "args": {
    "deviceId": "dev_9f32b47c2a8f4f8a",
    "type": "allowApp",
    "target": "com.supercell.clashofclans",
    "reason": "I want to play with my friends on weekends."
  }
}
```

```json
{
  "requestId": "req_a2f91c7e5d8240f3",
  "status": "pending"
}
```

</CodeGroup>

After a successful response, close the modal and show a confirmation state indicating that the request is awaiting approval.

## App Settings view — Self-managed

Self-managed users see the same configuration sections (AppMode, Categories, Whitelist, Blacklist, Network Rules) but can update settings directly without approval workflows.

<Callout kind="info">

Self-managed flows call the same `api.devices.apps.getConfig` for reads but use direct update APIs for writes. Do not reuse the mentee request modal; instead, apply changes immediately and surface any errors inline.

</Callout>

### View configuration

Reuse `api.devices.apps.getConfig` with the same input and output contract as the mentee/child flow.

- Use `appMode` and `appFilter` to drive toggles and selectors.
- Allow inline editing of `allowedApps` and `blockedApps`, for example through multi-select lists or search-and-add patterns.
- From the App Details page, link to this App Settings view so self-managed users can adjust how the app behaves on their device.

### Direct updates: apps configuration

Use `Devices.apps.update` to change app-related settings on a device.

#### Inputs

<ParamField body="device.id" param-type="string" required="true">

Identifier of the device whose app configuration you want to update.

</ParamField>

<ParamField body="appFilter" param-type="string" required="false">

Updated filter policy for apps. Omit this field to leave the existing filter unchanged.

</ParamField>

<ParamField body="allowedApps" param-type="string[]" required="false">

Full list of allowed app bundle identifiers to set on the device. Provide this when the user modifies the whitelist.

</ParamField>

<ParamField body="blockedApps" param-type="string[]" required="false">

Full list of blocked app bundle identifiers to set on the device. Provide this when the user modifies the blacklist.

</ParamField>

#### Outputs

<ParamField body="appMode" param-type="string" required="false">

Resulting app mode after the update, if the API returns it.

</ParamField>

<ParamField body="appFilter" param-type="string" required="false">

Resulting filter policy after the update.

</ParamField>

<ParamField body="allowedApps" param-type="string[]" required="false">

Resulting allowed apps list after the update.

</ParamField>

<ParamField body="blockedApps" param-type="string[]" required="false">

Resulting blocked apps list after the update.

</ParamField>

#### Example: update allowed and blocked apps

<CodeGroup tabs="Request,Response" show-lines={true}>

```json
{
  "method": "Devices.apps.update",
  "args": {
    "device": {
      "id": "dev_9f32b47c2a8f4f8a"
    },
    "appFilter": "whitelist",
    "allowedApps": [
      "com.shomri.companion",
      "com.duolingo.DuolingoMobile",
      "com.google.Chrome"
    ],
    "blockedApps": [
      "com.supercell.clashofclans"
    ]
  }
}
```

```json
{
  "appMode": "selfManaged",
  "appFilter": "whitelist",
  "allowedApps": [
    "com.shomri.companion",
    "com.duolingo.DuolingoMobile",
    "com.google.Chrome"
  ],
  "blockedApps": [
    "com.supercell.clashofclans"
  ]
}
```

</CodeGroup>

### Direct updates: network rules

Use `Devices.restrictions.update` to change network-related policies, such as domain filters or firewall-style rules that affect how apps access the web.

#### Inputs

<ParamField body="device.id" param-type="string" required="true">

Identifier of the device whose network rules you are updating.

</ParamField>

<ParamField body="rules" param-type="object[]" required="true">

Array of network rule objects to apply to the device. Define the rule shape consistently with your restrictions model.

</ParamField>

#### Example: update network rules

<CodeGroup tabs="Request" show-lines={true}>

```json
{
  "method": "Devices.restrictions.update",
  "args": {
    "device": {
      "id": "dev_9f32b47c2a8f4f8a"
    },
    "rules": [
      {
        "id": "rule_allow_learning",
        "action": "allow",
        "domains": ["khanacademy.org", "duolingo.com"]
      },
      {
        "id": "rule_block_social",
        "action": "block",
        "domains": ["tiktok.com", "instagram.com"]
      }
    ]
  }
}
```

</CodeGroup>

Apply optimistic UI updates where appropriate, but always reconcile with the API response or a follow-up `api.devices.apps.getConfig` call to keep the App Settings view in sync with the actual device state.
