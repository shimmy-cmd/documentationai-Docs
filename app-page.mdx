## Purpose

- Present detailed information for a selected app and hand off installation to the Apple App Store.
- Expose app-related configuration for a device, with different behaviors for mentee/child versus self-managed devices.

<Callout kind="info">

App Settings use the same underlying configuration API for both mentee/child and self-managed devices. The difference is how users change settings: mentees submit requests, while self-managed users update configuration directly.

</Callout>

## App Details page

The App Details page mirrors an app store product page: it shows app metadata, description, screenshots, and a primary button that opens an overlay to download the app from the Apple App Store.

### What the user sees

- App icon, name, and publisher.
- Ratings and category (if available from metadata).
- Long description and key highlights.
- Screenshots, typically in a horizontal gallery.
- A primary **Download from App Store** button.

When the user clicks the download button, show an overlay that deep-links into the Apple App Store for the app.

### Data source: Apple Lookup API

Use the Apple Lookup API to fetch app metadata based on the App Store `trackId`.

#### Inputs

<ParamField query="trackId" param-type="number" required="true">

The Apple App Store identifier for the app. Persist this on the app record in your catalog and pass it to the lookup call.

</ParamField>

#### Outputs (metadata shape)

Treat the Apple Lookup API response as `{ metadata }` for the UI. The exact Apple payload is large; pull out the fields you need for the screen.

<ParamField body="metadata" param-type="object" required="true">

Container for the app metadata returned by the Apple Lookup API.

</ParamField>

<ParamField body="metadata.name" param-type="string">

Human-readable app name used for the header.

</ParamField>

<ParamField body="metadata.bundleId" param-type="string">

Bundle identifier for the app, used to correlate with device configuration when needed.

</ParamField>

<ParamField body="metadata.developerName" param-type="string">

Publisher or developer name displayed under the app name.

</ParamField>

<ParamField body="metadata.description" param-type="string">

Full description text displayed in the details section.

</ParamField>

<ParamField body="metadata.screenshots" param-type="string[]">

List of screenshot image URLs displayed in the gallery.

</ParamField>

<ParamField body="metadata.category" param-type="string">

Primary category label for the app.

</ParamField>

<ParamField body="metadata.rating" param-type="number">

Average rating score if available.

</ParamField>

<ParamField body="metadata.storeUrl" param-type="string">

Deep link URL to the app in the Apple App Store, used in the download overlay.

</ParamField>

#### Example: Apple lookup call

<CodeGroup tabs="Request,Response" show-lines={true}>

```bash
# Request: lookup app metadata by trackId
curl "https://itunes.apple.com/lookup?id=871761612"
```

```json
{
  "resultCount": 1,
  "results": [
    {
      "trackId": 871761612,
      "trackName": "Shomri Companion",
      "bundleId": "com.shomri.companion",
      "sellerName": "Shomri Labs Ltd",
      "description": "Shomri Companion helps families manage device usage and app access.",
      "primaryGenreName": "Utilities",
      "averageUserRating": 4.6,
      "screenshotUrls": [
        "https://is5-ssl.mzstatic.com/image/thumb/Screen1.png",
        "https://is5-ssl.mzstatic.com/image/thumb/Screen2.png"
      ],
      "trackViewUrl": "https://apps.apple.com/app/id871761612"
    }
  ]
}
```

</CodeGroup>

Map this response into the `{ metadata }` shape your UI expects.

## App Settings — Mentee/Child

The mentee/child App Settings view shows the current configuration for a device and lets the user request, but not apply, changes.

<Callout kind="info">

Mentees cannot change policy directly. When they tap a setting they do not have, open a modal to submit a change request. The request then flows through your approval process.

</Callout>

### View configuration

Use `api.devices.apps.getConfig` to populate the App Settings view for a specific device.

#### Inputs

<ParamField body="deviceId" param-type="string" required="true">

Identifier of the device whose app configuration you are viewing.

</ParamField>

#### Outputs

<ParamField body="appMode" param-type="string" required="true">

Current mode for the device, such as focus or leisure. Use this to drive high-level messaging and which controls are enabled.

</ParamField>

<ParamField body="appFilter" param-type="string" required="true">

Active filter policy for apps, such as category-based or whitelist-only.

</ParamField>

<ParamField body="allowedApps" param-type="string[]" required="true">

List of app bundle identifiers that are explicitly allowed on the device.

</ParamField>

<ParamField body="blockedApps" param-type="string[]" required="true">

List of app bundle identifiers that are explicitly blocked on the device.

</ParamField>

#### Example: config fetch

<CodeGroup tabs="Request,Response" show-lines={true}>

```json
{
  "method": "api.devices.apps.getConfig",
  "args": {
    "deviceId": "dev_9f32b47c2a8f4f8a"
  }
}
```

```json
{
  "appMode": "guided",
  "appFilter": "categories",
  "allowedApps": [
    "com.shomri.companion",
    "com.duolingo.DuolingoMobile"
  ],
  "blockedApps": [
    "com.supercell.clashofclans"
  ]
}
```

</CodeGroup>

Render sections for AppMode, Categories, Whitelist, Blacklist, and Network Rules. For mentees, treat these sections as mostly read-only, with entry points into the request flow.

### Request app or policy change

When a mentee interacts with a configuration they do not have (for example, tapping a blocked app they want to allow), trigger a modal.

#### Modal behavior

- Show the current value and the requested new value.
- Let the mentee specify a reason (optional).
- On submit, call `request.create.appRequest`.

<Callout kind="tip">

You will likely define additional request types for specific changes, such as network rules updates or mode changes. Keep the modal flexible to support multiple `type` and `target` values.

</Callout>

#### Inputs

<ParamField body="deviceId" param-type="string" required="true">

Device the request applies to.

</ParamField>

<ParamField body="type" param-type="string" required="true">

Kind of change requested, such as `allowApp`, `blockApp`, or `changeMode`.

</ParamField>

<ParamField body="target" param-type="string" required="true">

Identifier for what is changing. For app changes, use the app bundle identifier; for mode changes, use the target mode name.

</ParamField>

<ParamField body="reason" param-type="string" required="false">

Free-text explanation from the mentee about why they are requesting the change.

</ParamField>

#### Outputs

<ParamField body="requestId" param-type="string" required="true">

Unique identifier for the created request, used to track approval status.

</ParamField>

<ParamField body="status" param-type="string" required="true">

Initial status of the request, such as `pending`.

</ParamField>

#### Example: change request

<CodeGroup tabs="Request,Response" show-lines={true}>

```json
{
  "method": "request.create.appRequest",
  "args": {
    "deviceId": "dev_9f32b47c2a8f4f8a",
    "type": "allowApp",
    "target": "com.supercell.clashofclans",
    "reason": "I want to play with my friends on weekends."
  }
}
```

```json
{
  "requestId": "req_a2f91c7e5d8240f3",
  "status": "pending"
}
```

</CodeGroup>

After a successful response, close the modal and show a confirmation state indicating that the request is awaiting approval.

## App Settings — Self-managed

Self-managed users see the same configuration sections (AppMode, Categories, Whitelist, Blacklist, Network Rules) but can update settings directly without approval workflows.

<Callout kind="info">

Self-managed flows call the same `api.devices.apps.getConfig` for reads but use direct update APIs for writes. Avoid reusing the mentee request modal; instead, apply changes immediately and surface any errors inline.

</Callout>

### View configuration

Reuse `api.devices.apps.getConfig` with the same input and output contract as the mentee/child flow.

- Use `appMode` and `appFilter` to drive toggles and selectors.
- Allow inline editing of `allowedApps` and `blockedApps`, for example through multi-select lists or search-and-add patterns.

### Direct updates: apps configuration

Use `Devices.apps.update` to change app-related settings on a device.

#### Inputs

<ParamField body="device.id" param-type="string" required="true">

Identifier of the device whose app configuration you want to update.

</ParamField>

<ParamField body="appFilter" param-type="string" required="false">

Updated filter policy for apps. Omit this field to leave the existing filter unchanged.

</ParamField>

<ParamField body="allowedApps" param-type="string[]" required="false">

Full list of allowed app bundle identifiers to set on the device. Provide this when the user modifies the whitelist.

</ParamField>

<ParamField body="blockedApps" param-type="string[]" required="false">

Full list of blocked app bundle identifiers to set on the device. Provide this when the user modifies the blacklist.

</ParamField>

#### Outputs

<ParamField body="appMode" param-type="string" required="false">

Resulting app mode after the update, if the API returns it.

</ParamField>

<ParamField body="appFilter" param-type="string" required="false">

Resulting filter policy after the update.

</ParamField>

<ParamField body="allowedApps" param-type="string[]" required="false">

Resulting allowed apps list after the update.

</ParamField>

<ParamField body="blockedApps" param-type="string[]" required="false">

Resulting blocked apps list after the update.

</ParamField>

#### Example: update allowed and blocked apps

<CodeGroup tabs="Request,Response" show-lines={true}>

```json
{
  "method": "Devices.apps.update",
  "args": {
    "device": {
      "id": "dev_9f32b47c2a8f4f8a"
    },
    "appFilter": "whitelist",
    "allowedApps": [
      "com.shomri.companion",
      "com.duolingo.DuolingoMobile",
      "com.google.Chrome"
    ],
    "blockedApps": [
      "com.supercell.clashofclans"
    ]
  }
}
```

```json
{
  "appMode": "selfManaged",
  "appFilter": "whitelist",
  "allowedApps": [
    "com.shomri.companion",
    "com.duolingo.DuolingoMobile",
    "com.google.Chrome"
  ],
  "blockedApps": [
    "com.supercell.clashofclans"
  ]
}
```

</CodeGroup>

### Direct updates: network rules

Use `Devices.restrictions.update` to change network-related policies, such as domain filters or firewall-style rules.

#### Inputs

<ParamField body="device.id" param-type="string" required="true">

Identifier of the device whose network rules you are updating.

</ParamField>

<ParamField body="rules" param-type="object[]" required="true">

Array of network rule objects to apply to the device. Define the rule shape consistently with your restrictions model.

</ParamField>

#### Example: update network rules

<CodeGroup tabs="Request" show-lines={true}>

```json
{
  "method": "Devices.restrictions.update",
  "args": {
    "device": {
      "id": "dev_9f32b47c2a8f4f8a"
    },
    "rules": [
      {
        "id": "rule_allow_learning",
        "action": "allow",
        "domains": ["khanacademy.org", "duolingo.com"]
      },
      {
        "id": "rule_block_social",
        "action": "block",
        "domains": ["tiktok.com", "instagram.com"]
      }
    ]
  }
}
```

</CodeGroup>

Apply optimistic UI updates where appropriate, but always reconcile with the API response or a follow-up `api.devices.apps.getConfig` call to keep the App Settings page in sync.
